# 소재 레이더 기획서

작성일: 2026-10-15

## 1. 개요

소재 레이더는 연예·스포츠 분야에서 지금 뜨는 소재를 자동으로 모으고, 카드뉴스로 만들 가치가 있는지 점수와 근거를 보여주는 웹 도구다.

**만드는 목적**

- 실무 목적: 하루 3~4개 카드뉴스 소재를 더 빨리, 더 근거 있게 고른다.
- 학습 목적: Orca와 GitHub로 이슈 작성 → 브랜치 → PR → 리뷰 → 머지 → 자동 배포의 개발 워크플로를 직접 익힌다. 사내 카드뉴스·영상 툴 개선 논의에서 개발팀과 같은 언어로 이야기하는 것이 최종 목표다.

**설계 대원칙: 지금은 작게, 구조는 미래까지**

MVP는 카테고리 2개, 소스 2개로 작게 시작한다. 하지만 카테고리, 소스, 플랫폼, 점수 기준은 모두 나중에 코드 수정 없이 추가·교체할 수 있게 설계한다.

**이 문서를 읽는 법**

- 나(기획자): 1~11장은 무엇을 왜 만드는지, 12장은 작업 순서, 14장은 용어 풀이.
- Orca 에이전트(Claude Code): 이 문서 전체가 작업 명세다. 특히 4장(구조), 8장(데이터 구조), 12장(이슈), 13장(작업 규칙)을 반드시 따른다.

## 2. 문제 정의와 사용자 시나리오

하루 3~4개를 발행하려면 매일 여러 번 소재를 찾아야 하는데, 지금은 인스타·뉴스·포털을 눈으로 돌아다니고 성과도 눈으로만 확인한다.

**지금의 문제**

- 소재 탐색에 시간이 많이 들고, 발견했을 땐 이미 늦은 경우가 많다.
- 같은 카드뉴스를 인스타·유튜브·네이버클립에 동시에 올리는데 성과가 플랫폼마다 크게 달라, 무엇이 잘 됐는지 판단할 수 없다.
- 그래서 "이 소재가 잘 먹힐까"를 감으로만 판단한다.

**사용자**

- 1차: 나 (카드뉴스 담당자, 연예·스포츠)
- 2차: 같은 팀 기획·제작자 (나중에 확장)

**핵심 장면**

1. 출근 직후: 레이더를 열고 "지금 뜨는 것"과 "곧 올 것"에서 오전 소재 1~2개를 찜한다.
2. 오후·저녁: 3~4시간마다 갱신된 보드를 다시 열어 상승 중인 새 소재를 확인한다.
3. 발행 후: 소재 상태를 "발행"으로 바꾸고 플랫폼별 게시물을 연결한다.
4. 주 1회: 지난주 게시물의 플랫폼별 성과 숫자를 입력한다 (게시물당 1분 이내).

**성공 기준**

- 사용 2주 후, 발행한 카드뉴스 중 절반 이상이 레이더에서 출발했다.
- 소재를 고르는 데 걸리는 시간이 체감상 줄었다.
- 1개월 후, "어떤 유형이 어느 플랫폼에서 잘 되는지"를 데이터로 말할 수 있다.

## 3. 범위

MVP는 "소재를 모으고, 거르고, 보여주고, 성과를 기록한다"까지만 한다. 나머지는 단계별로 붙인다.

| 단계 | 포함 기능 | 목표 시점 |
| --- | --- | --- |
| MVP | 연예·스포츠 2개 카테고리, 구글 트렌드 + 뉴스 RSS 수집, 3~4시간 주기 자동 수집, 1단계 규칙 필터, 화제성 점수와 국면 표시, 3칸 보드, 소재 상태 흐름, 예정 이벤트 수동 입력, 워치리스트, 플랫폼별 성과 수동 입력, 패스 이유 기록, "이미 다룬 소재" 표시 | 약 2주 |
| 2단계 | 네이버 데이터랩 연동, 인스타 해시태그 연동(spike 결과에 따라), 유튜브 조회수 자동 수집, 한도 장부, 즉석 검색(GitHub Actions 수동 실행), 슬랙 알림 | MVP 후 2~4주 |
| 3단계 | AI 앵글 제안, 적합도 점수 자동 보정, 업로드 시간대 분석, 카테고리 추가, 즉석 검색 서버리스 전환 | 데이터 1~2개월 축적 후 |

**하지 않을 것**

- 카드뉴스 제작 자체 (사내 툴의 역할)
- 인스타·유튜브 자동 게시
- 경쟁 계정 모니터링
- 기사 본문, 사진 저장 (헤드라인과 링크만 저장한다. 저작권·초상권 리스크 때문)
- 인스타 크롤링 (이용약관 위반)

## 4. 시스템 구조와 확장 원칙

외부 소스에서 모은 데이터가 수집 파이프라인을 거쳐 데이터베이스에 쌓이고, 웹 보드가 그것을 보여준다. 소스는 모듈로 갈아끼우고, 판단 규칙은 설정 파일에서 바꾼다.

```text
[외부 소스]                [수집 파이프라인]              [저장·화면]
                          GitHub Actions · 3~4시간마다
 구글 트렌드 (MVP) ─┐
 뉴스 RSS   (MVP) ─┤──▶  수집 모듈
 네이버 데이터랩 (2) ┤          │
 인스타 해시태그 (2) ┤          ▼
 유튜브 조회수   (2) ┘     규칙 필터 · 사건 묶기
                                │
                                ▼
                          점수 · 국면 계산 ──────────▶  데이터베이스
                                ▲                       (소재·수집 기록·게시물·성과
                                │                        워치리스트·이벤트·한도 장부)
                          설정 파일 (config)                  ▲│
                          카테고리·소스·가중치·제외어           │▼
                                                         웹 보드 (배포)
                                                         3칸 보드·성과 입력·관리 화면
                                                              ▲│  찜·패스·성과 입력
                                                              │▼
                                                         나 (담당자)
(2) = 2단계에 추가
```

수집 파이프라인은 3~4시간마다 자동 실행된다. 담당자가 찜, 패스, 성과 입력을 하면 웹 보드를 통해 같은 데이터베이스에 기록된다.

**기술 선택**

| 부분 | 선택 | 이유 |
| --- | --- | --- |
| 수집·필터·점수 | Python | 데이터 처리 도구가 많고 코드가 읽기 쉽다 |
| 자동 실행 | GitHub Actions | 레포 안에서 무료로 예약 실행된다 |
| 데이터베이스 | Supabase (PostgreSQL) | 무료로 시작, 웹 화면에서 바로 읽고 쓰기, 로그인 기능 포함 |
| 웹 화면 | React + TypeScript (Vite) | 에이전트가 잘 다루는 조합이다 |
| 배포 | GitHub Pages | 무료, main에 머지되면 자동 배포 |

찜, 패스, 성과 입력처럼 사람이 넣는 기록을 저장해야 하므로 MVP부터 데이터베이스를 둔다.

**확장 원칙**

1. **소스 = 독립 모듈**: 모든 수집 모듈은 같은 형식(소스, 키워드, 헤드라인, 링크, 언론사, 수집 시각)으로 결과를 내놓는다. 새 소스 추가는 모듈 하나 + sources.yaml 항목 하나로 끝난다.
2. **규칙 = 설정 파일**: 카테고리, 가중치, 기준값, 제외어는 코드에 쓰지 않고 config에서 읽는다.
3. **값으로 저장**: 플랫폼, 지표, 상태, 태그는 고정 칸이 아니라 값으로 저장한다.
4. **실패 격리**: 한 소스가 실패해도 나머지는 계속 동작한다.
5. **한도 장부 경유**: 한도가 있는 API는 장부를 거쳐서만 호출한다.

**폴더 구조**

```text
sojae-radar/
├─ config/              설정 파일 (categories, sources, scoring, exclude)
├─ collector/
│  ├─ sources/          소스별 수집 모듈 (trends.py, rss.py …)
│  ├─ filter.py         규칙 필터 · 사건 묶기
│  └─ score.py          점수 · 국면 계산
├─ web/                 웹 보드
├─ db/                  데이터베이스 생성 스크립트
├─ tests/               테스트와 샘플 응답
├─ docs/                PLAN.md, DATA.md
└─ .github/workflows/   자동 실행 설정
```

## 5. 소재 판단 로직

싼 필터로 먼저 대부분을 거르고, 한도가 있는 비싼 확인은 끝까지 살아남은 소수에만 쓴다. 점수는 "화제성"과 "적합도" 두 개로 나눈다.

**깔때기 4단계**

1. **후보 수집 (한도 없음)**: 구글 트렌드 한국 급상승어, 연예·스포츠 뉴스 RSS에서 후보를 넓게 모은다.
2. **규칙 필터 (API 비용 0)**
    - 같은 사건 묶기: 같은 기사 제목에 함께 나온 키워드는 한 소재로 합친다.
    - 카테고리 판별: 연예·스포츠 섹션 RSS 헤드라인에 등장한 키워드만 통과시킨다.
    - 교차 등장: 트렌드와 뉴스 양쪽에 나온 것을 우선한다.
    - 최소 보도량: 다룬 언론사가 기준 수 이상이어야 한다 (기준은 설정값).
    - 제외: 제외 키워드, 이미 패스한 소재, 최근에 확인한 소재.
3. **상승 국면 확인 (네이버 데이터랩, 2단계)**: 2단계 통과 상위 10~20개만 검색량 추이를 확인한다.
4. **인스타 반응 확인 (2단계)**: 점수가 경계선에 있는 소재만 해시태그로 조회한다.

탈락한 후보는 버리지 않고 "관찰 중" 목록에 남겨 다음 수집 때 다시 평가한다. 작게 시작한 대형 소재를 놓치지 않기 위해서다.

**국면 표시**

최근 수집 회차들 사이의 언급량 변화로 판단한다.

| 국면 | 판단 | 담당자 행동 |
| --- | --- | --- |
| 상승 중 | 언급량이 계속 늘고 있음 | 지금 바로 만들기 좋음 |
| 정점 | 증가가 멈춤 | 차별화된 각도가 있을 때만 |
| 하락 | 언급량이 줄고 있음 | 패스하거나 정리형으로 |

**① 화제성 점수 (처음부터 사용)**

상승 국면 + 교차 등장 + 보도량 + 워치리스트 가산점 + (2단계부터) 인스타 반응. 각 항목의 가중치는 설정 파일에 두고, 처음엔 감으로 정한 뒤 주 1회 조정한다. 카테고리마다 규모가 다르므로 점수는 카테고리 안에서의 상대 순위로 보정한다.

**② 적합도 점수 (데이터가 쌓이며 생김)**

- 소재 유형 태그별 과거 성과 (이슈형, 기록형, 이벤트형, 인물형으로 시작)
- 패스 이유 기록 (이미 늦음, 우리 톤 아님, 루머성, 너무 마이너)
- 플랫폼별 "평소 대비 배수" (7장)

운영 순서: 1~2주차는 화제성 점수만 쓴다. 3~4주차부터 쌓인 기록을 보고 가중치를 사람이 조정한다. 플랫폼당 200건 이상 쌓이면 간단한 통계 모델로 자동 보정을 검토한다.

**신뢰도 표시**

MVP에서는 "다룬 언론사 수" 하나만 보여준다. 공식 입장 여부, 루머성 표현 판별은 정확도가 낮아 3단계로 미룬다. 레이더는 판단을 대신하지 않고, 담당자가 빠르게 판단할 근거를 보여주는 역할이다.

## 6. 외부 API 한도 관리

한도가 있는 API는 "한도 장부"를 거쳐서만 호출한다. 장부에 남은 한도가 없으면 코드가 호출을 건너뛴다.

**인스타그램 해시태그 검색 (2단계)**

- 제약: 계정당 7일 동안 서로 다른 해시태그 30개. 최근 게시물 조회는 24시간 이내 글만, 최대 250개. Meta 앱 심사와 비즈니스 인증이 필요하다. ([Meta 문서](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/hashtag-search))
- 활용할 규칙: 이미 조회한 해시태그를 7일 안에 다시 조회하면 한도에 추가로 잡히지 않는다.
- 슬롯 배분: 고정 슬롯 약 10개(자주 다루는 팀·아티스트, 주초 등록 후 그 주 내내 재조회) + 유동 슬롯 약 20개(경계선 소재 확인용, 하루 2~3개).
- 사용 원칙: 점수가 확실히 높거나 낮은 소재는 조회하지 않는다. 경계선 소재의 결정에만 쓴다.
- 해시태그는 공백과 이모지를 쓸 수 없으므로 키워드를 해시태그 형태로 바꾸는 변환 규칙이 필요하다.

**네이버 데이터랩 (2단계)**

일일 호출 한도와 한 번에 비교 가능한 키워드 수 제한이 있다. 결과는 절대 검색량이 아니라 상대 지표다. 깔때기 2단계를 통과한 상위 소재에만 쓴다.

**한도 장부 규칙**

- 호출할 때마다 소스, 키워드, 시각을 기록한다.
- 호출 전에 장부로 남은 한도를 계산하고, 부족하면 건너뛰고 로그를 남긴다.
- 보드 화면 구석에 "이번 주 인스타 남은 한도: N개"를 표시한다.
- API 키는 코드에 넣지 않고 GitHub Secrets에만 보관한다.

## 7. 플랫폼별 성과 기록

플랫폼끼리 숫자를 직접 비교하지 않고, 각 플랫폼 안에서 "평소 대비 몇 배인가"로 본다. 그래야 "이 소재는 어느 플랫폼에서 먹히는가"가 보인다.

**평소 대비 배수**

```text
배수 = 이번 게시물의 지표 ÷ 같은 플랫폼 최근 20개 게시물 지표의 중앙값
```

**플랫폼별 핵심 지표 (하나씩만)**

| 플랫폼 | 지표 | 수집 방식 |
| --- | --- | --- |
| 인스타그램 | 저장 + 공유 | 수동 입력 (회사 계정 권한 필요) |
| 유튜브 | 조회수 | MVP는 수동, 2단계에 API 자동 수집 |
| 네이버클립 | 재생수 | 수동 입력 (공개 API 여부 확인 필요) |

**기록 규칙**

- 기록 시점은 "발행 3일 후"로 고정한다. 숫자는 시간이 지날수록 변하므로 시점이 같아야 공정하다.
- 주 1회 몰아서 입력한다. 하루 3~4개 × 3개 플랫폼이라 주 70~80개 숫자이므로, 입력 화면은 한 주 게시물이 표로 뜨고 숫자만 넣는 형태로 만든다.
- 시작 전에 최근 1개월치(약 100개)를 소급 입력한다. 오래된 게시물은 현재 누적값을 쓰고 "소급"으로 표시한다.
- 업로드 시각도 함께 기록한다. 나중에 "소재 문제인지 시간대 문제인지"를 구분하기 위해서다.

**검증할 가설**

네이버 데이터랩 검색량이 높은 소재가 네이버클립에서 더 잘 된다. 데이터랩을 이미 깔때기에서 조회하므로 추가 비용 없이 검증할 수 있다.

## 8. 데이터 구조

데이터는 두 곳에 나눠 둔다. 자주 안 바뀌는 "규칙"은 레포의 설정 파일에, 매일 쌓이는 "기록"은 데이터베이스에 둔다. 이 구분이 확장성의 핵심이다.

**설정 파일 (레포의 config 폴더, 변경은 PR로)**

| 파일 | 담는 것 | 확장 방법 |
| --- | --- | --- |
| categories.yaml | 카테고리 이름, 켜짐 여부, 카테고리별 RSS 목록 | 카테고리 추가 = 항목 하나 추가 |
| sources.yaml | 소스 종류, 주소, 켜짐 여부 | 소스 추가 = 항목 + 수집 모듈 하나 |
| scoring.yaml | 점수 가중치, 최소 보도량, 국면 판단 기준 | 숫자만 바꾸고 PR로 이력 남김 |
| exclude.yaml | 제외 키워드 | 항목 추가 |

**데이터베이스 (기록)**

| 이름 | 의미 | 주요 필드 |
| --- | --- | --- |
| mentions | 수집한 원시 데이터 한 줄 | 소스, 키워드, 헤드라인, 링크, 언론사, 수집 시각 |
| topics | 묶어서 정리한 소재 | 제목, 키워드 목록, 카테고리, 상태, 국면, 화제성 점수, 적합도 점수, 언론사 수, 유형 태그, 패스 이유, 처음·마지막 발견 시각 |
| topic_snapshots | 수집 회차별 소재 기록 | 소재, 수집 시각, 언급 수, 점수 |
| posts | 발행한 게시물 | 소재, 플랫폼, 링크, 발행 시각 |
| post_metrics | 게시물 성과 | 게시물, 지표 이름, 값, 측정 시각, 소급 여부 |
| watchlist | 관심 인물·팀·작품 | 이름, 종류, 카테고리, 해시태그 |
| events | 예정 이벤트 | 제목, 날짜, 카테고리, 메모, 연결된 소재 |
| api_ledger | 한도 장부 | 소스, 조회어, 호출 시각 |

**관계**

- 소재 1개 → 수집 회차 기록 여러 개 (국면 계산용)
- 소재 1개 → 게시물 여러 개 (플랫폼별) → 게시물마다 성과 여러 개
- 플랫폼, 지표 이름, 상태, 유형 태그는 고정된 칸이 아니라 값으로 저장한다. 그래서 틱톡이나 새 지표가 생겨도 구조를 바꿀 필요가 없다.

**소재 상태 값**

관찰 중 → 발견 → 찜 → 제작 중 → 발행, 또는 어느 단계에서든 패스.

## 9. 화면 구성

메인은 한 화면 3칸 보드다. 소재를 고르는 데 필요한 것은 탭을 오가지 않고 한 화면에서 끝낸다.

**메인 보드 (한 화면 3칸)**

| 칸 | 보여주는 것 | 정렬 |
| --- | --- | --- |
| 지금 뜨는 것 | 상위 5개는 크게, 나머지는 접어둠. 카드마다 제목, 카테고리, 국면 표시, 화제성 점수, 언론사 수, "이미 다룬 소재" 표시 | 점수순 |
| 곧 올 것 | 7일 안의 예정 이벤트 (컴백, 첫방, 시상식, 주요 경기) | 날짜순 |
| 내 찜 목록 | 찜·제작 중 상태 소재 | 찜한 순 |

상단에는 카테고리 필터(연예, 스포츠, 전체), 마지막 수집 시각, 이번 주 인스타 남은 한도(2단계)를 둔다.

**소재 카드에서 바로 할 수 있는 것**

- 찜하기, 제작 중으로 바꾸기, 발행으로 바꾸기
- 패스: 이유 버튼 4개 중 하나를 누르면 끝 (이미 늦음, 우리 톤 아님, 루머성, 너무 마이너)
- 유형 태그 붙이기 (이슈형, 기록형, 이벤트형, 인물형)

**별도 페이지**

- 소재 상세: 관련 헤드라인과 링크, 언급 수 추이, 메모, 연결된 게시물
- 성과 입력: 이번 주 발행 게시물이 표로 뜨고, 플랫폼별 숫자만 입력
- 워치리스트·이벤트 관리: 추가, 수정, 삭제
- 성과 보기 (2단계부터): 유형별·플랫폼별 평소 대비 배수

**화면 원칙**

- 휴대폰에서도 보드를 볼 수 있어야 한다 (이동 중 확인).
- 처음 버전은 예쁨보다 빠름을 우선한다.

## 10. 리스크와 한계

가장 큰 리스크는 기술이 아니라 "성과 입력이 귀찮아서 멈추는 것"이다. 입력이 멈추면 적합도 점수 전체가 멈춘다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 성과 수동 입력 중단 | 적합도 점수가 학습되지 않음 | 게시물당 1분 입력 화면, 유튜브 자동 수집 우선, 주 1회 고정 |
| 인스타 API 접근 불가 (개인 계정은 비즈니스 인증이 어려움) | 인스타 반응 신호 없음 | 교체 가능한 모듈로 분리, spike 이슈로 먼저 확인, 안 되면 사람 입력으로 대체 |
| 루머·미확인 이슈가 상위에 뜸 | 오보·명예훼손 리스크 | 언론사 수 표시, "루머성" 패스 이유로 학습, 최종 판단은 사람 |
| 키워드 사전에 없는 신조어·신인 | 소재 누락 | 트렌드 발견형을 기본으로, 워치리스트는 보조. 탈락 후보는 "관찰 중"에 보관 |
| 같은 사건이 여러 키워드로 쪼개짐 | 중복 소재, 한도 낭비 | 헤드라인 동시 등장으로 묶기 |
| 외부 소스 형식 변경·중단 | 수집 실패 | 소스별 모듈 분리, 실패 시 다른 소스는 계속 동작, 실패 알림 |
| 범위가 계속 커짐 | MVP가 끝나지 않음 | 3장의 단계 구분을 지키고, 새 아이디어는 이슈로만 적어둠 |

**데이터의 한계**

하루 3~4개 발행 규모에서 1~2개월 데이터는 "증명"이 아니라 "경향"이다. 알고리즘 노출 운, 업로드 시간대, 같은 날 다른 게시물과의 경쟁이 성과에 섞여 있다는 점을 감안한다.

## 11. 로드맵과 일정

MVP는 약 2주, 3단계는 성과 데이터가 플랫폼당 100건 이상 쌓인 뒤 시작한다. 다음 단계로 넘어가는 기준은 날짜가 아니라 게이트 조건이다.

| 단계 | 시점 | 내용 | 다음 단계로 넘어가는 게이트 |
| --- | --- | --- | --- |
| 준비 | 0주차 | 성과 소급 입력, 인스타 spike, 레포·DB 세팅 | 기준선 확보 (플랫폼별 중앙값) |
| MVP | 1~2주차 | 수집·필터·점수, 3칸 보드, 상태·성과 입력, 자동 수집·배포 | MVP 완료 (매일 보드로 소재 선택) |
| 2단계 | 3~6주차 | 데이터랩·인스타, 유튜브 자동 수집, 한도 장부, 즉석 검색·알림 | 성과 데이터 충분 (플랫폼당 100건 이상) |
| 3단계 | 2~3개월차 | AI 앵글 제안, 적합도 자동 보정, 업로드 시간대 분석, 카테고리 추가 | — |

하루 3~4개 발행 기준으로 플랫폼당 약 1주면 25건, 1개월이면 100건이 쌓인다. 기간은 학습 속도에 따라 늘어날 수 있고, 기능보다 게이트 통과를 우선한다.

## 13. 에이전트 작업 규칙

Orca에서 일하는 모든 에이전트(Claude Code 등)는 아래 규칙을 따른다. 이 장은 레포의 CLAUDE.md에도 그대로 넣는다.

**작업 방식**

1. 이슈 하나 = worktree 하나 = 브랜치 하나 = PR 하나. 이슈 범위를 넘는 변경은 하지 않고, 필요하면 새 이슈를 제안한다.
2. 작업 전 docs/PLAN.md와 docs/DATA.md를 읽는다. 데이터 형식을 바꿔야 하면 코드보다 먼저 DATA.md 변경을 PR로 올린다.
3. PR 설명에는 무엇을, 왜 바꿨는지, 어떻게 확인했는지를 코딩을 모르는 사람도 이해할 말로 쓴다.
4. 완료 조건(체크리스트)을 모두 만족했는지 PR에 표시한다.

**확장성 규칙**

- 카테고리, 소스, 가중치, 기준값을 코드에 직접 쓰지 않는다. 항상 config 폴더의 설정 파일에서 읽는다.
- 새 소스는 공통 수집 모듈 형식을 따르는 독립 모듈로 추가한다. 다른 모듈을 수정하지 않는다.
- 플랫폼, 지표, 상태, 태그는 값으로 저장한다. 새 값이 생겨도 데이터 구조를 바꾸지 않는다.

**안전 규칙**

- API 키, 비밀번호는 코드와 커밋에 절대 넣지 않는다. GitHub Secrets와 환경변수만 쓴다.
- 한도가 있는 API는 반드시 한도 장부를 거쳐 호출한다.
- 기사 본문, 이미지는 저장하지 않는다. 인스타 크롤링은 하지 않는다.
- 외부 API가 실패해도 전체가 멈추지 않게 한다.

**품질 규칙**

- 계산 로직(필터, 점수, 국면, 배수)에는 테스트를 붙인다.
- 외부 API 테스트는 실제 호출 대신 저장된 샘플 응답을 쓴다.

## 14. 용어 풀이

| 용어 | 쉬운 설명 |
| --- | --- |
| 레포 (저장소) | 프로젝트의 모든 파일과 변경 기록을 담는 GitHub 폴더 |
| 이슈 | 해야 할 일 하나를 적은 카드. 목적과 완료 조건을 함께 적는다 |
| 브랜치 | 원본을 건드리지 않고 따로 작업하는 복사본 줄기 |
| worktree | 브랜치마다 따로 열어둔 작업 폴더. Orca는 에이전트마다 하나씩 준다 |
| 커밋 | 변경 내용을 한 번 저장한 기록 |
| PR (풀 리퀘스트) | "이 변경을 원본에 합쳐도 될까요?" 요청. 여기서 리뷰한다 |
| 머지 | 리뷰가 끝난 변경을 원본(main)에 합치는 것 |
| 충돌 (conflict) | 두 작업이 같은 곳을 다르게 고쳐서 자동으로 못 합치는 상황 |
| GitHub Actions | 정해진 시간이나 조건에 코드를 자동 실행해주는 GitHub 기능 |
| GitHub Secrets | API 키 같은 비밀값을 안전하게 보관하는 곳 |
| API | 다른 서비스에 데이터를 달라고 요청하는 공식 창구 |
| API 한도 | 정해진 기간에 요청할 수 있는 최대 횟수 |
| RSS | 언론사가 새 기사 목록을 기계가 읽기 쉽게 내보내는 형식 |
| 데이터베이스 | 기록을 표 형태로 저장하고 꺼내 쓰는 곳 |
| 설정 파일 (config) | 코드를 고치지 않고 동작을 바꾸는 값들을 모아둔 파일 |
| 모듈 | 한 가지 일만 하는 독립된 코드 덩어리. 갈아끼울 수 있다 |
| 테스트 | 코드가 의도대로 동작하는지 자동으로 확인하는 코드 |
| 배포 | 만든 프로그램을 다른 사람이 쓸 수 있게 인터넷에 올리는 것 |
| spike | 될지 안 될지 모르는 기술을 짧게 시험해보는 탐색 작업 |
| MVP | 핵심 가치를 확인할 수 있는 가장 작은 첫 버전 |
| 중앙값 | 숫자를 크기순으로 줄 세웠을 때 가운데 값. 튀는 값에 덜 흔들린다 |
